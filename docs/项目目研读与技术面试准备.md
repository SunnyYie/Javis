## 一、项目定位与介绍口径

### 1.1 一句话定位

Larkway 是连接飞书与本地原生编码 Agent 的轻量桥接系统：团队通过飞书发起工作，由 Claude Code、Codex 或 pi 在本地工作目录执行，再把回答、执行状态和协作记录反馈到飞书。

它不是重新实现大模型推理循环的平台，也不是已经具备严格租户隔离的企业任务执行沙箱。

### 1.2 它实际解决的问题

| 原有问题 | 项目的解决方式 | 需要保留的边界 |
|---|---|---|
| 编码 Agent 主要由个人在终端使用 | 飞书成为团队统一入口 | 不等于所有人可以无边界地使用宿主权限 |
| 聊天助手不理解真实项目 | 在真实工作目录调用原生 Agent 和工具 | 回答质量仍受模型、代码上下文和工具影响 |
| 请求发在群里后缺少后续 | 话题、任务、评论、交付信号关联 | Agent 交付不等于人工验收 |
| 多人请求相互阻塞或串上下文 | 按会话串行、跨会话受控并行 | 会话隔离不等于工作目录隔离 |
| 网络与进程异常导致丢单、重复执行 | 去重、补取、持久化、取消与恢复 | 不提供端到端 exactly-once 业务执行保证 |
| 自建完整 Agent 框架成本较高 | 复用原生 CLI 的登录、工具和会话 | 同时承担原生协议变化的适配成本 |

### 1.3 30 秒介绍

> 我最近深入研读了 Larkway。它把飞书话题连接到本地 Claude Code、Codex 等原生编码 Agent，让团队可以在聊天中发起工作并跟踪结果。我关注的不是简单的消息转发，而是三个工程问题：如何保持原生会话连续性，如何处理重复消息和长任务，以及如何让跨机器人交接可追溯。当前我的角色是源码研究和方案分析，已有实现不是我的个人开发成果。

### 1.4 90 秒介绍

> Larkway 采用薄桥接架构。入站侧接收飞书消息，完成格式归一化、去重和话题路由；执行侧通过统一 AgentRunner 接口适配不同原生运行时；出站侧把回答、工具进度和结果转换成流式卡片，并可关联飞书任务。
>
> 我认为最值得研究的是它对状态边界的处理。第一，同一原生会话不能同时有多个执行者，所以同话题排队，不同话题才受控并行。第二，收到消息、Agent 执行结束、结果投递成功、人工验收是不同状态，不能互相替代。第三，多机器人交接先写入真实飞书消息，再用相同消息 ID 做本地直递和 WebSocket 回流去重。
>
> 它也有明确取舍：多个话题可能共享工作目录，默认权限较宽，原生审批和执行中 steering 尚未完整桥接。因此它更适合受信任团队中的自托管工具，而不是直接当作对外多租户平台。

介绍结束时停下来，让面试官选择方向。不要主动连续展开全部模块。

## 二、真正值得介绍的亮点

### 2.1 优先级与价值

| 优先级 | 亮点 | 为什么值得讲 | 可展开的关键问题 |
|---|---|---|---|
| P0 | 原生运行时适配与事件协议 | 不是重新包装一次模型 API，而是保留成熟 Agent 能力并统一消费 | JSON-RPC、流式事件、能力差异、协议兼容 |
| P0 | 会话连续性与并发一致性 | AI 应用从单人演示进入多人使用时的关键门槛 | 队列键、session 身份、单写者、共享目录 |
| P0 | 消息可靠性与失败恢复 | 体现真实网络和失败场景下的工程能力 | in-flight、seen、补取、重试、副作用幂等 |
| P0 | 长任务与进程生命周期 | Agent 任务可能持续很久，不能照搬普通 HTTP 请求模型 | cancel、timeout、真实退出、热池、后台任务 |
| P1 | 跨 Agent 可靠交接 | 同时考虑团队可见性、通知通路和重复消费 | mirror-first、真实消息 ID、结构化 mention |
| P1 | 流式 UI 与终态一致性 | 与前端背景高度相关，展示异步状态和交互建模能力 | delta/snapshot、节流、版本序列、收尾降级 |
| P1 | 人工验收与任务语义 | 技术实现和业务流程衔接得比较成熟 | turn 完成、交付、验收的区分 |
| P2 | 性能可观测与原生对照 | 能解释优化收益来自哪里，而不是只说“更快” | 分段计时、冷热分组、token 口径、失败样本 |

### 2.2 不建议作为主亮点

- “用了 TypeScript、Node.js、WebSocket”：是技术背景，不是独立解决的问题。
- “有管理后台”：先说明降低了什么配置和运维成本，再讲实现。
- “支持多个大模型”：本项目主要适配原生 Agent 运行时，不是直接搭建模型路由服务。
- “用了多 Agent”：必须继续说明谁决策、如何交接、怎样去重、失败如何恢复。
- “共享知识库”：当前主要是文件和 Git 组织方式，不能包装成向量检索、Embedding 或复杂 RAG。
- “全自动开发上线”：具体任务能力来自原生 Agent、目标仓库工具和授权环境，桥接层本身不保证全生命周期成功。

### 2.3 根据岗位选择主线

**前端结合 Agent 岗位**：优先讲事件驱动 UI、流式终态一致性、任务状态与人工确认，再下钻运行时接口。

**Agent 工程岗位**：优先讲协议适配、会话所有权、取消与恢复、可信权限边界。

**全栈平台岗位**：优先讲接入可靠性、存储与并发边界、可观测性，以及向多实例演进的条件。

## 三、架构与关键不变量

### 3.1 主链路

```text
用户 @机器人 / 任务评论 / 定时触发 / Agent 显式交接
                       |
                       v
飞书接入：WebSocket、事件归一化、mention 与路由事实
                       |
                       v
消息准入：seen / in-flight 去重、补取恢复
                       |
                       v
执行调度：同会话串行，跨会话受控并行
                       |
                       v
AgentRunner
  ├─ Claude：原生流式协议
  ├─ Codex：app-server --stdio / JSON-RPC
  └─ pi：冷启动 JSON / 可选热池 RPC
                       |
                       v
统一事件：回答、工具活动、进度、结果、usage
                       |
                       v
飞书流式卡片 / 终稿降级 / 任务信号 / 显式 handoff
```

以下是便于理解的逻辑划分，不是新增的业务调度架构：

- **管理面**：机器人定义、连接配置、模型与运行参数、本地管理 UI。
- **运行面**：消息接收、会话定位、进程调用、事件转换、结果投递。
- **原生 Agent**：理解任务、规划步骤、调用工具、操作仓库。
- **人**：授权、决策，以及最终业务验收。

### 3.2 面试中必须守住的不变量

1. 同一原生会话在同一时刻不能有两个冲突写者。
2. 入站排队键必须覆盖实际会话归属，不能让两个排队链最终落到同一 session。
3. 收到消息后不能立即当作已成功处理，否则异常时难以恢复。
4. 取消等待不等于底层进程已经停止。
5. 模型输出完成不等于外部结果已经投递。
6. 消息去重不等于业务副作用全局幂等。
7. 正式答案、执行活动和不确定的兼容回退必须可区分。
8. 任务验收不应由一次进程成功退出隐式决定。
9. Markdown 权限说明和身份提示不能替代机械权限控制。
10. 对已有实现、设计建议和个人贡献使用不同表述。

### 3.3 四种不能混为一谈的“完成”

| 维度 | 含义 | 不能推出什么 |
|---|---|---|
| 消息处理终态 | 本次入站事件进入了某种终态 | 不能推出模型答案正确 |
| 原生 turn 结束 | 一轮原生执行返回结果 | 不能推出进程退出，或后台工作全部结束 |
| 结果已交付 | 用户能看到结果或交付说明 | 不能推出业务验收通过 |
| 人工验收完成 | 人确认符合需求并完成任务 | 不能反向证明每个中间环节都没有失败 |

## 四、技术面试官：十组递进问答

### T01：为什么采用薄桥接，而不是自己实现 Agent 框架？

**主问题**

这个项目看起来就是在飞书和 CLI 之间转发消息，为什么还需要专门设计架构？

**首轮回答**

> 单次演示确实可以通过启动 CLI 再回传文本实现。但团队持续使用时，需要保持会话、处理长任务、恢复断线、避免重复执行，并让结果回到正确的话题。项目把这些确定性的接入和运行问题放在桥接层，把任务理解、规划和工具选择保留在原生 Agent 中。这样既复用原生能力，也避免在桥接层维护第二套不断漂移的 Agent 逻辑。

**完整设计思路**

1. 先划分职责：桥接层管理消息与执行协议，Agent 管理业务判断。
2. 复用原生登录、工具、Skills、配置和会话，而不是复制一套模型调用循环。
3. 只抽象确实共用的运行接口，不强求各后端拥有完全相同的能力。
4. 用结构化声明表达卡片或交接需求，不通过猜测自然语言来决定工作流。
5. 将协议适配的成本集中在后端边界，避免飞书 UI 直接依赖某个 CLI 的事件格式。

**追问 1：不做编排，为什么还有队列和定时器？**

队列负责限制并发、保持执行顺序；定时器负责在指定时间提供一个触发事实。它们是运行调度。决定“先开发还是先测试”“失败后转给谁”“任务是否值得继续”属于业务编排，应由 Agent 或人决定。两者不是一回事。

**追问 2：什么时候应该放弃薄桥接，使用工作流引擎？**

当需求变成跨主机持久任务、可审计审批、长时间挂起恢复、补偿事务和明确的状态转换时，仅靠进程和消息队列不够。可以增加独立执行控制层，但应先定义状态、恢复与幂等协议，而不是把业务分支继续塞进消息 handler。

**追问 3：复用 CLI 有什么代价？**

依赖协议版本、宿主环境、原生登录状态和进程行为；能力变化可能比普通 HTTP API 更复杂。需要记录版本、维护协议回归样本、限制兼容回退范围。薄桥接减少自建能力，并不会免除适配和维护成本。

**收束点**：我关注的是职责边界和运行可靠性，不把“封装 CLI”本身当作创新。

**依据**：E01、E02、E03。

### T02：如何统一不同 Agent 的协议，又保留原生能力？

**主问题**

Claude、Codex 的事件结构不同，你会怎样设计统一接口？

**首轮回答**

> 项目通过 AgentRunner 暴露 run，返回事件异步迭代器、结果 Promise 和取消入口。适配器把各自原生事件归一化，展示层只消费回答、工具、进度和结果等稳定语义。Codex 当前走 app-server JSON-RPC，并优先使用原生 final_answer 阶段；不是把所有 stdout 都当成用户答案。

**完整设计思路**

- 输入分成任务内容、session 指针、cwd、模型参数、权限、取消和预算。
- 输出使用带 `type` 的联合类型，让 TypeScript 对不同事件分支进行收窄。
- `answer_delta` 表示追加，`answer_snapshot` 表示替换，不能混用。
- `internal_text` 与正式答案分开；原生协议明确了答案阶段，就优先使用协议，而不是文本猜测。
- 保留未知 `raw` 事件用于兼容和诊断，但不能自动把所有未知文本暴露给用户。
- 某个选项只对特定后端有效时，应明确支持范围，而不是假装所有后端完全等价。

**追问 1：为什么需要 snapshot？只用 delta 不行吗？**

原生完成事件可能提供权威全文，期间可能漏收部分增量，或者最终内容与先前流式内容不同。snapshot 可以校准本地答案缓冲。若把全文当成增量追加，用户会看到重复；如果始终只拼 delta，又可能残留不完整答案。

**追问 2：流里同时有工具消息和回答，如何避免串到一起？**

在适配器里根据原生事件类型和阶段区分通道，而不是到 UI 再用关键词过滤。工具活动进入进度面，正式回答进入答案缓冲。当前还存在严格条件下的末段内部文本救援回退，必须承认这个兼容路径，不能宣称所有展示内容都有绝对可信的答案通道证明。

**追问 3：新增后端要做哪些工作？**

实现统一接口，建立原生事件映射和终态规则，处理启动失败、取消、预算、session 恢复，再注册后端工厂。补充冷启动与复用场景测试，并核实权限、usage 和用户输入能力差异。设计建议是增加显式 capability 描述，帮助 UI 禁用不支持的控制；不能声称当前已有完整的能力协商协议。

**危险追问：两个后端都叫 acceptEdits，所以权限相同吗？**

不相同。当前 Codex 对非 `ask` 模式映射到较宽的访问策略，pi 本身也没有等价权限系统。统一字段名不代表统一安全保证。

**依据**：E02、E03、E12。

### T03：如何保证同一会话不并发执行，同时支持多人使用？

**主问题**

五个人同时发消息，系统如何决定排队还是并行？

**首轮回答**

> 先确定消息最终归属的会话，再按会话维度维护串行 Promise 链。不同会话可以并行，但共享一个处理器内的并发信号量，当前上限是 5。同一个 Agent 的多个话题可能共享 cwd，所以这个机制只解决会话执行顺序，不自动解决代码文件冲突。

**完整设计思路**

1. SessionStore 用话题与 bot 的组合定位原生 session。
2. 排队键需要考虑根消息、引用父消息及可选的单聊 sticky session。
3. 队列键允许比会话键更保守：少一些并行可以接受，不能让同一 session 被分到不同执行链。
4. 在事件收到时记录 receipt 并 touch 会话，不能等到真正开始执行才记录，以免排队被误判为丢失或闲置。
5. 同会话执行链结束后，只删除仍指向自己的队列项，避免删除后续刚追加的链。
6. 释放并发槽位放在清理路径，防止异常让额度永久泄漏。

**追问 1：为什么排队键不直接等于 message_id？**

同一话题的每条消息拥有不同 message_id，但可能恢复同一个原生 session。按 message_id 排队会让它们并行写同一上下文。引用任务卡片还可能在后续解析时重新确定会话归属，所以准入阶段必须覆盖这种归属，不能只看最表面的 ID。

**追问 2：并发上限 5 是全局上限吗？**

当前这个信号量位于每个处理器实例内，不应描述为整个多机器人部署共享的全局限额。多 bot、更多进程时，宿主总并发仍可能更高。真正的主机级配额需要单独的资源控制。

**追问 3：为什么队列不会一直无限增长？**

已有实现会回收完成的队列链，并合并部分兼容的排队纯文本跟进，但这不等于完整背压。设计建议是增加队列长度或等待时间上限、明确“已接收但未开始”的反馈、超限拒绝和取消策略。不能把当前 Map 清理说成已经解决所有积压问题。

**追问 4：不同话题同时修改同一文件怎么办？**

session ID 只能隔离上下文，不能隔离 Git checkout。应由目标项目规则或执行环境使用独立 worktree、分支和工作目录，并定义合并与冲突处理；必要时对仓库级危险操作串行化。当前不能声称自动提供逐任务独立沙箱。

**依据**：E04、E05、E11。

### T04：WebSocket 重复、断线和恢复，怎样避免丢消息或重复工作？

**主问题**

为什么不能收到飞书消息后立即写入一个“已处理”集合？

**首轮回答**

> 收到和处理成功不是同一件事。如果一接收就永久标记，随后进程异常，这条请求会被恢复逻辑跳过。当前设计区分 in-flight 和 seen：接收时先占用，成功后再标记完成；失败时释放，并在合适的补取窗口重新发现。重连后从历史消息补取，再通过同一套准入规则去重。

**完整设计思路**

```text
未占用消息 --准入--> in-flight
in-flight --处理确认--> seen，并持久化
in-flight --可恢复失败--> 释放占用，登记恢复窗口
重复 live / local / replay --准入检查--> 跳过
```

这是说明消息机制的简化图，不代表所有业务结果都一律重跑。实际失败路径还需要区分“Agent 尚未执行”与“执行结束但投递失败”。

- 每个 bot 应有独立 SDK 缓存，否则同一条同时 @ 两个机器人的消息可能被第二个误去重。
- 断线窗口应覆盖最后确认健康的时刻；机器休眠时，“发现断线的时间”可能晚于真正失联时间。
- 历史接口要处理分页；未完整拉取不能把恢复窗口标记为完成。
- 拉取失败和事件失败要有限重试，并防止毒消息无限循环。
- 显式停止所丢弃的排队消息也需要确认，防止恢复机制把用户取消的工作重新拉起。

**追问 1：这样就实现 exactly-once 了吗？**

没有。并发副本可通过去重避免重复准入，但跨崩溃的业务副作用仍不保证恰好一次。例如外部 PR 已创建，进程在记录成功前退出，恢复可能再次执行。需要下游幂等键、结果查询和“执行已发生”的独立凭据。不能把消息去重升级为业务事务保证。

**追问 2：Agent 做完了，只有卡片发送失败，能否整条重试？**

不应无脑重跑。应优先补投已经生成的结果，或在明确记录的边界上恢复。当前接口有禁止自动 replay 的选项来处理这类风险，但也不能说已经拥有通用持久交付事务。扩展时应拆开执行结果和投递结果，并保留产物索引。

**追问 3：为什么每个 bot 的去重缓存必须独立？**

消息 ID 标识的是飞书消息，不是“某机器人已经消费”的事实。同一消息同时 @ A 和 B，两者都应该收到。正确的消费身份至少要包含机器人维度；进程级共享同一去重空间会把合法的多消费者误判成重复。

**追问 4：恢复为什么不是实时、无限保证？**

依赖平台历史接口、读取权限、时间范围、分页完整性、缓存保留与进程状态。对于超出恢复窗口或平台不可读的消息，系统仍可能无法补回，必须有可见告警和人工补偿入口。

**依据**：E06、E07、E08。

### T05：会话为什么用文件存储？原子 rename 能解决所有一致性问题吗？

**主问题**

用 JSON 文件存 session，看起来是不是不够专业？

**首轮回答**

> 对单机、自托管、低到中等规模的桥接工具，文件存储部署简单，也容易排查。关键不是是否用了数据库，而是写入模型是否正确。项目把写入串行化，执行时取最新快照，写到唯一临时文件再 rename，降低并发覆盖和半写文件风险。但这不是跨进程事务，也不能宣称断电后一定不丢数据。

**完整设计思路**

1. session 记录保存原生 session ID、bot、话题、cwd、backend 和运行元数据。
2. cwd 或 backend 发生变化时不能继续盲目恢复旧 session，应启动新原生上下文并明确说明。
3. 高频 touch 先改内存、延迟刷盘，重要 put/delete 及时刷盘。
4. 通过写队列避免多个异步写者同时落盘；唯一临时文件避免共用 `.tmp` 的覆盖问题。
5. 写失败传回调用者，但不能让失败的 Promise 永久阻塞整个后续写队列。
6. fresh-start 标记保留话题身份等元数据，避免直接删记录导致重要关联丢失。

**追问 1：有 rename，为什么还需要写队列？**

rename 只保证一次替换的可见性，不保证多次写入按业务期望的顺序落盘。较早的旧快照如果更晚 rename，仍可能覆盖新状态；固定临时路径还可能产生文件内容交错。串行化、取快照时机、临时路径和原子替换解决的是不同问题。

**追问 2：进程突然退出或磁盘满了怎么办？**

唯一临时文件可能遗留；写失败需要清理和告警，当前已有失败临时文件的 best-effort 清理。rename 没有自动提供 fsync 级断电持久保证。若要求强持久化，应明确文件及目录刷盘策略，或采用有事务和恢复语义的存储。

**追问 3：什么时候换 SQLite 或数据库？**

出现多个写进程、需要事务更新多类状态、复杂查询、长期审计或数据量显著增长时。SQLite 适合仍以单机为主的事务需求；多实例需要统一状态与所有权协议。换数据库本身不会自动解决重复执行。

**追问 4：session ID 没变，能证明记忆没丢吗？**

不能。还需要检查实际加载的原生历史、目录、指令和模型行为。应设计有修改、撤销、插入和跨话题冲突的用例，而不是只检查一个 ID 或让模型复述暗号。

**依据**：E05、E09、E11、E16。

### T06：长任务、取消、超时和热进程池怎样设计？

**主问题**

用户点停止后，界面显示已停止，为什么还需要关心进程是否真的退出？

**首轮回答**

> 停止等待和停止执行是两个状态。界面可以先有界返回，但旧进程如果还在写文件，马上启动同 session 的替代进程会形成两个写者。项目在运行接口中区分 turn 的 done 与真实 processExited，并在热池里跟踪退役进程，避免把“请求已结束”当成“资源已释放”。

**完整设计思路**

- `AbortSignal` 或停止命令表达取消意图；执行器负责向原生协议或进程传递中断。
- 显式总预算从一次 `runner.run()` 调用计算，包括启动、推理、工具和等待，不因输出事件续期。
- 当前默认不强加总时限，idle 默认用于提示等待，而不是把静默直接判为失败。
- 首次中断原因保留，晚到的 timeout 或 cancel 不应覆盖真实原因。
- 热进程复用需要匹配实际配置，不能让新模型、权限或 Skills 配置错误地复用旧进程。
- 已退役但尚未真实退出的进程不能视为可复用，也不能允许相同 session 立刻出现新写者。
- 原生后台任务可能让首个结果只是让出执行；不能在仍有后台工作的情况下提前释放会话归属。

**追问 1：一直没有输出，为什么不直接杀掉？**

无输出可能是正常长工具调用，也可能是模型等待或真正卡死。应结合在途工具、原生事件、用户选择和显式预算处理。默认先给可解释的等待状态与停止入口；强制终止应是明确配置，而不是用任意静默阈值冒充完成判断。

**追问 2：取消和超时同时发生怎么办？**

用首次原因决定终态，清理动作保持幂等，取消监听器和定时器在终态后释放。清理进程的信号不能误标为用户中断；已经真正完成的 turn 也不能被晚到的定时器改写为失败。

**追问 3：pooled=true 是否说明这是一次热启动？**

不是。池管理的新进程首轮也可以是 pooled。恢复原生历史是否已经在同一进程加载，要看 `resumeMode` 等信息。需要区分进程归池、历史冷恢复和同进程续轮。

**追问 4：为什么热池不能设计成完全统一？**

不同 runtime 的协议和进程组织不同。Claude、Codex、pi 的复用粒度、原生线程加载、后台任务和退役方式不完全一样。统一接口应约束可观察语义，不应强迫底层都按同一种缓存键或进程数量模型实现。

**追问 5：bridge 重启以后，原任务还能持续执行吗？**

不能据现有会话持久化作此保证。会话恢复不等于跨主机或跨 bridge 重启的持久任务执行。需要真正的执行所有权、状态日志和恢复协议，才能设计这种能力。

**依据**：E02、E10、E11、E16。

### T07：流式卡片怎样避免乱序、重复和最终答案被覆盖？

**主问题**

模型不断输出，为什么不每收到一个 token 就 PATCH 一次飞书卡片？

**首轮回答**

> token 产生速度和平台更新能力不同，逐个更新会放大 API 成本和乱序风险。当前设计维护本地答案缓冲，按节流周期提交，区分增量与快照，使用序列化更新链与递增序列控制写入。最终稿采用整卡替换，并先处理已经排队的旧更新，避免旧进度覆盖终稿。

**完整设计思路**

1. 本地状态接收高频事件，外部卡片更新使用较低频率。
2. 当前默认更新间隔为 250ms；达到软预算后退避，默认软预算是 240 次，不是超过就永久冻结。
3. 相同答案不重复提交，减少无效调用。
4. 流式过程中更新答案元素；工具和执行活动使用独立展示语义。
5. finalize 停止新的普通更新，协调已排队调用，再用权威内容替换终稿。
6. 终稿失败时保留明确状态并尝试修复或另发兜底，不能继续假装成功。
7. 可选 state 文件需要校验格式和本轮新鲜度，避免上一轮结果重现。

**追问 1：单调递增 sequence 是否足以解决所有乱序？**

不够。还需要本地调用排序、终稿屏障、忽略过期状态和平台自己的序列规则。只给请求加数字但允许旧调用在终稿后继续提交，仍可能失败或破坏展示。应把“接受事件”和“提交外部更新”作为两个阶段建模。

**追问 2：为什么最后整卡替换，不继续打字？**

终稿可能来自新鲜状态文件、失败或停止说明，与流式缓冲不同。整卡替换能一次确定最终结构，减少重复终稿调用和中间不一致，代价是最终内容可能跳变。这是正确性、延迟与视觉连续性的取舍。

**追问 3：state.json 格式错了怎么办？**

使用 Zod 校验，并对可降级字段进行有限救援，保留诊断。当前存在对特定裸引号问题的窄修复，但不应把它泛化成任意损坏 JSON 都能安全恢复。状态无效时仍应尽可能展示本轮答案，同时明确状态缺失，不能复用陈旧结果。

**追问 4：展示的“思考”是否就是完整内部推理？**

不能这样承诺。应准确说展示的是原生运行时提供的 reasoning summary、活动和工具信息。正式答案、进度与诊断需要分层，敏感参数或工具结果还要控制暴露范围。不能把 UI 命名等同于模型内部过程的完整披露。

**追问 5：这与前端能力有什么关系？**

本质是高频事件驱动下的状态一致性：loading 不代表工作一定在推进，取消不代表资源已释放，最终快照也不能被迟到事件覆盖。React、原生 DOM、桌面 UI 都会遇到这些问题，关键在状态模型与异步协调，而不是组件库选择。

**依据**：E12、E13、E14。

### T08：为什么任务完成要由人确认？

**主问题**

Agent 已经返回成功，直接把飞书任务勾成完成，不是更自动化吗？

**首轮回答**

> 执行成功、交付和验收属于不同语义。进程返回成功只能说明一轮执行结束，可能只是回答了问题或提交了中间产物。当前推荐的任务维护模式通过评论汇报关键进展、阻塞和交付，由人决定是否满足需求并完成任务，避免自动完成掩盖未验收的问题。

**完整设计思路**

- Agent 判断任务是否值得跟踪，通过结构化声明请求建卡。
- bridge 机械创建任务、写入话题回链、尝试添加发起人为关注人，再建立关联。
- 进展通过评论承载，利用原生推送；不把描述更新当作用户必然看到的通知。
- 截止时间调整应保留理由，阻塞应说明需要什么人类输入。
- 任务评论可回流原会话，形成持续协作。
- 已交付后等待人工完成的窗口不能继续被误判为停滞。
- 任务投影失败采用降级，不应让已经完成的 Agent 主工作完全失去反馈。

**追问 1：这是否违反 thin bridge，因为它调用了任务 API？**

结构化声明已经表达“创建这张任务”的决定，桥接层执行确定性投影，不替模型判断业务步骤。边界在于是否做了业务决策，不是所有外部 API 都绝对不能调用。应该遵守项目明确建立的任务协议，而不是任意扩展桥接层的业务能力。

**追问 2：为什么任务评论回流比一直改描述更合适？**

评论更符合事件式协作，也能产生推送；描述适合相对稳定的背景与回链。设计依据是平台行为和用户可见性，不是“评论在技术上更先进”。高频工具日志也不应全部灌入评论，否则会形成通知噪声。

**追问 3：任务被删了怎么办？**

删除关联不等于重建任务。当前 comment 模式通过轮询等路径发现任务不存在，存在短暂的映射滞后；显式 create 有额外核对路径。用户应获得清楚的降级说明，不能无授权重建被人删除的任务。

**追问 4：旧代码里有自动 complete/reopen，是否矛盾？**

仓库保留历史 full 模式兼容路径。当前推荐主路径使用 comment 模式，交付与人工完成分离。需要先确认用户采用哪条路径，不能只读到旧分支就把历史能力当作当前默认。

**依据**：E15、E17。

### T09：多 Agent 交接怎样做到可靠且可追溯？

**主问题**

为什么不直接调用另一个机器人的本地函数，还要发一次飞书消息？

**首轮回答**

> 本地调用延迟低，但团队看不到交接记录，其他进程里的机器人也收不到。项目先发送带真实 mention 的飞书消息，拿到真实 message_id，再对同进程机器人做本地直递。直递与 WebSocket 副本共享 ID，并通过目标机器人的去重入口竞争准入，从而兼顾可追溯和同进程低延迟。

**完整设计思路**

1. 交接必须由 Agent 显式声明目标和原文，桥接层不猜自然语言中的分工意图。
2. 目标解析到已知 peer，mention 使用对应应用作用域内可用的身份信息。
3. 在原话题中创建真实 post，并使用稳定的发送幂等键。
4. 发送失败则不执行本地交接，避免出现没有外部记录的隐形任务。
5. 发送成功后，同进程目标可以直接进入正常入站通路；跨进程目标依赖 WebSocket 等已有接入。
6. 本地副本与网络副本共用真实消息 ID；谁先进入都使用同一套 seen/in-flight 规则。
7. 同进程交接可以等待约定的卡片和任务信号屏障；不能把所有跨进程交接都说成严格晚于上游终稿。

**追问 1：发送成功后，bridge 在本地直递前崩溃怎么办？**

真实飞书消息仍然存在，目标可通过正常接入和补取发现。这样降低了只依赖内存调用的脆弱性，但仍依赖飞书可读性和恢复窗口，不是消息中间件级无限持久保证。

**追问 2：发送请求超时，实际上已经发出，再重试会重复吗？**

应复用同一请求身份与幂等键，不应该每次换一个 ID。项目交接发送基于触发消息、条目和目标生成稳定键。平台幂等有其范围，不能进一步声称所有后续业务副作用都天然幂等。

**追问 3：A 交给 B，B 再交回 A，怎样避免循环？**

不能只靠同一消息 ID 去重，因为每次新交接可能生成新消息。设计建议是增加交接链标识、深度或预算、相同意图冷却、循环可见告警，以及人类终止入口。它们是可提出的护栏，不应把当前消息去重描述为已彻底解决语义循环。

**追问 4：这算多 Agent 智能编排吗？**

它是多 Agent 协作通道。是否拆任务、由谁负责、何时重试是 Agent 或人决定的；bridge 负责可靠执行已声明的交接。不要把机制层能力夸大成自动规划系统。

**依据**：E08、E18。

### T10：如何证明优化有效，而不是只把 prompt 变短？

**主问题**

你说复用进程、精简 prompt 会更快，如何严谨验证？

**首轮回答**

> 先验证任务正确性，再比较性能。把端到端延迟拆成消息接入、排队、启动前准备、原生运行和结果投递，分别观察首轮与续轮、冷恢复与同进程复用。prompt 字符数只是注入规模，不是 token 或业务效率；结果应来自可比任务、多次样本，并保留失败。

**完整设计思路**

1. 固定代码版本、CLI 版本、模型、effort、权限、工具、Skills 和文件初始快照。
2. native 与 bridge 各用独立 session，在各自实验组内保持续轮连续。
3. 设置有状态变更的任务，验证文件、回答和最终交付，而不是仅看退出码。
4. 记录入站、入队、开始处理、runner 调用与完成、finalize 开始与结束等时间点。
5. 分别观察首个内容事件、首个正式答案和用户最终可见结果，不能混称首 token。
6. 优化后检查质量、失败率、资源和成本，不只看成功样本的耗时。

**追问 1：怎样算桥接开销？**

对每个样本计算 `该样本接收至完成耗时 - 该样本 runner 耗时`，再对这些差值做统计。不能直接用两组耗时的中位数相减，冒充开销中位数。具体 API 的贡献还需要自己的 span。

**追问 2：输入 token 减少 50%，是否能说成本降低 50%？**

不能直接推出。要区分缓存读、缓存写、未缓存输入、输出及模型计费方式。订阅额度也不等同于 API 单价成本。Claude 和 Codex 的 usage 口径不同，Codex 累计计数应取合适的差值，重放快照不能重复求和。

**追问 3：续轮 delta prompt 为什么不会丢上下文？**

不把固定说明重复注入，是依赖原生 session 历史与原生指令加载。cwd、backend 或 session 改变时需要重新提供完整必要契约。长上下文压缩后的有效性仍需单独测试，不能因为短对话通过就宣称永远不丢信息。

**追问 4：先启动模型、卡片并行创建是否一定更快？**

可能降低关键路径等待，但新话题通常由卡片建立。Agent 如果过早向飞书回复，消息可能落到话题外。因此当前有按续轮启用的可选策略；优化不能以破坏路由语义为代价。

**当前可说与不可说**

可说：项目已有这些观测点、优化机制和对照方法。不可说：本人完成了某百分比提速、某 token 节省或业务人效提升。本文未取得这类个人实测证据。

**依据**：E02、E11、E16。

## 五、技术 Leader：六组递进问答

### L01：为什么这个系统不能直接向全公司或外部客户开放？

**主问题**

如果我让你把它推给全公司，你首先会担心什么？

**首轮回答**

> 首先是权限和影响范围，而不是先扩容。它把聊天入口连接到能读写文件、执行命令并继承宿主工具凭据的 Agent。默认权限较宽，会话目录和 bot 身份配置也不是 OS 隔离。应先明确可信用户、可操作仓库、数据出网和高风险动作，再决定部署与审批机制。

**完整设计思路**

1. 识别资产：源码、凭据、宿主文件、飞书数据、仓库写权限和部署能力。
2. 划分信任边界：消息发送者、飞书、bridge、Agent、工具、模型服务商。
3. 减小默认权限：测试群白名单、专用低权限账号、独立工作目录、最少凭据。
4. 对高风险动作做机械授权，不能只依赖 AGENTS.md 中的一段要求。
5. 对工具输出、网页和仓库内容按不可信数据处理，避免指令注入改变授权。
6. 记录必要审计与结果，但对 token、环境变量和敏感参数脱敏。
7. 需要对外服务时，再引入真正的租户隔离、配额、身份认证与安全执行环境。

**追问 1：把权限写进 Markdown，让模型遵守，不够吗？**

不够。那是行为提示和审计说明，不是文件系统或工具执行 gate。即使模型理解正确，也可能遭遇恶意内容、工具缺陷或配置错误。关键权限需要由模型无法绕过的控制层执行。

**追问 2：删除 OPENAI_API_KEY 是否已经隔离凭据？**

没有。它主要避免特定后端被环境变量切换到 API key 计费，不等于清空宿主环境或隔离 Git 凭据。当前还可以继承 SSH agent、credential helper 等能力；pi 的 BYO-model 路径还需要透传自身 provider 凭据。

**追问 3：本地运行是否保证代码不出公司？**

不保证。代码和工具结果可能进入模型请求，回答也会经过飞书。必须审查数据流、模型服务条款、网络边界和企业策略，不能用“本地 Agent”替代完整的数据安全说明。

**追问 4：管理后台有 token，是否就达到企业级认证？**

不是。当前本机回环绑定和启动令牌适合本地管理工具，但不等于多用户身份体系、RBAC、SSO 或对恶意本机进程的隔离。若转为远程管理，应重新设计威胁模型和访问控制，而不是只把监听地址改成公网。

**依据**：E03、E11、E19。

### L02：如果用户量扩大十倍，如何演进？

**主问题**

是否加几个进程、接 Redis 队列就可以了？

**首轮回答**

> 不可以直接横向复制。当前有本地文件状态、进程内会话队列和 bot 内并发限制。多个实例可能抢同一消息、同时恢复同一原生 session，还可能共享同一个 checkout。扩容前必须先确定消息、会话和工作目录的所有权。

**完整设计思路**

- 先测瓶颈是模型额度、CPU/内存、队列等待、飞书 API 还是磁盘，不默认是 Node 吞吐问题。
- 对宿主总并发、单 bot、单用户或单工作区分别设置预算和背压。
- 多实例下将同一会话稳定路由到同一 owner，使用明确的占用与退役协议。
- 共享状态需要事务或版本控制，不能让多个进程继续写同一 JSON 文件。
- 任务执行目录也要隔离，不能只把消息交给不同 worker。
- 将结果产物与投递记录分开，便于失败后只补投，不重做业务动作。
- 资源使用和用户等待应可观测，超限应明确反馈，而不是无限积压。

**追问 1：加分布式锁不就解决了吗？**

锁过期时旧 worker 可能仍在运行，新的 worker 又拿到锁，会发生双写。需要租约、所有权检查、退役和 fencing；如果外部工具不能验证 fencing token，就不能声称锁已经完全阻断旧执行者。可能需要由受控执行服务代理危险操作。

**追问 2：是不是所有状态都放 Redis 就行？**

Redis 可以承担部分队列或短期状态，但持久性、恢复、审计、原生 session 文件和工作目录仍需要设计。技术选型不能代替一致性模型。先定义失败后的处理语义，再决定 Redis、数据库或持久队列的组合。

**追问 3：10 倍用户量是否一定需要分布式？**

不一定。Agent 工作的主要成本可能在模型与工具，单机通过配额、背压和资源分离即可承载。应根据实测的并发活跃数和任务时长做容量规划，而不是按注册用户数直接扩架构。

**追问 4：怎样设置 SLO？**

把接入成功、排队等待、启动延迟、执行结果、投递成功分开。长短任务分别定义可衡量目标，业务完成时间不能全部归因于桥接服务。本文没有现成生产 SLO 数据，不能编造可用性或延迟承诺。

**依据**：E04、E05、E06、E10。

### L03：如何制定测试策略，证明它真的可用？

**主问题**

单元测试很多，是不是就可以上线？

**首轮回答**

> 不可以。项目的单元测试主要通过模拟网络、子进程和时钟验证确定性逻辑，它们不能证明真实 CLI 协议、飞书权限和卡片回流都能工作。我会把纯逻辑回归、协议契约验证和真实链路验收分开，并保留失败证据。

**完整测试设计**

| 层级 | 重点 | 典型用例 |
|---|---|---|
| 纯单元 | 状态与算法 | session key、JSON 持久化、delta/snapshot、去重 |
| 协议适配 | 版本与事件序列 | 原生 init、工具调用、final、异常、取消乱序 |
| 模拟集成 | 多模块交互 | 同 topic 排队、跨 bot 缓存、local/WS 双路交接 |
| 真实 runtime | 实际任务和进程 | 修改临时文件、续轮修订、停止后确认真实退出 |
| 真实飞书 | 身份与传输 | 真人 @、原话题回帖、任务评论回流、最终卡片读回 |
| 故障与恢复 | 异常窗口 | 断线、分页失败、进程退出、投递失败、磁盘异常 |

**追问 1：如何测试上下文不串？**

不同话题使用互相冲突的事实、文件或约束，检查各自输出和实际操作。相同任务仅换两个 root ID 不足以检测串上下文；也要验证并行执行没有改到同一文件。

**追问 2：怎样验证取消，不只检查 UI 显示？**

检查后续副作用是否停止、进程是否真正退出、同 session 替代运行是否受到正确限制、其他会话是否继续。对退出未确认的情况保留失败证据，不能只等 done Promise resolve 就判通过。

**追问 3：真实 E2E 怎样避免影响正式环境？**

使用独立 `LARKWAY_HOME`、临时 workspace、专用测试群和唯一用例标识；避免相同 app 并行启动竞争订阅。事先准备部署恢复方案，结束后检查残留进程、配置和恢复补取。真实模型运行与飞书发送需要明确授权。

**追问 4：重试后成功可以算通过吗？**

可以报告“在指定重试策略下最终成功”，但应保留首轮失败、尝试次数和原因。不能静默删除失败样本，也不能把重试通过当作首次成功率。

**当前验证状态**

本文只阅读了测试代码与验证指南，没有执行以上测试。仓库存在某个测试用例，不代表其在当前环境已经通过。

**依据**：E07、E08、E09、E10、E13、E16。

### L04：如何证明有业务价值，应该看哪些指标？

**主问题**

这个项目技术做得复杂，团队为什么要用？

**首轮回答**

> 价值不在“机器人能聊天”，而在团队能否更低成本地发起工作、拿到有依据的结果，并减少追问和交接损耗。应先选择明确场景，例如代码口径查询、问题排查或低风险修改，再衡量首次有效结果时间、人工介入和验收结果，而不是用消息数量或 commit 数代替业务价值。

**指标设计建议**

- **接入漏斗**：可用账号或机器人配置完成率、首次成功任务比例。
- **任务结果**：按预先定义标准验收的成功率、人工返工和升级率。
- **协作效率**：从提出问题到首次有效结果的时间、追问次数、交接确认耗时。
- **可靠性**：投递成功率、重复准入事件、失败恢复比例、取消后异常副作用。
- **资源成本**：每个验收任务的 usage、机器资源和人工审查时间。
- **持续价值**：有实际任务的活跃用户、复用频率、持续使用场景。

**追问 1：成功率的分母是什么？**

应把进入约定任务范围的所有真实请求纳入，单独说明用户主动取消、超出支持范围和环境故障的处理。不能只统计成功结束且有完整日志的样本，否则启动失败和投递失败会被排除。

**追问 2：怎样证明是产品带来的提效？**

选择可比任务、相近难度、相同工具条件，记录原流程的人力时间和新流程的审查、纠错成本。使用前后对比或受控试点，并披露样本差异。单次快案例不能推导普遍百分比提效。

**追问 3：采用率和效率是不是同一个指标？**

不是。采用说明有人使用，效率需要任务结果与成本对比，质量又是另一维度。此前用户确认的脉芽采用数据属于另一个项目，不能迁移给 Larkway。

**追问 4：缺少数字时怎么介绍？**

如实讲清目标场景、机制和待测指标，不编造覆盖人数、节省工时或 SLA。完成真实试点后再补业务数据，并保留口径、周期和样本量。

### L05：让你继续建设，优先做什么，为什么？

**主问题**

下一阶段你会先补新功能，还是先重构代码？

**首轮回答**

> 先按风险和当前用户场景排序。如果要扩大使用范围，优先明确权限、执行所有权和原生审批缺口；如果仅面向受信任小团队，先补排队可见性、失败补投和关键链路验收。不会为了“架构更漂亮”先做大规模重写，也不会直接添加更多模型掩盖已有可靠性问题。

**建议优先级，尚非已完成工作**

1. 建立可重复的关键链路验收与分段指标。
2. 补齐排队、取消、结果投递的状态可见性和人工处理入口。
3. 针对目标场景补机械权限与原生审批往返。
4. 根据真实瓶颈改善资源配额与运行隔离。
5. 在稳定契约下逐步拆分复杂 handler，不同时重写所有行为。

**追问 1：原生审批怎样接入飞书？**

设计需要保存原生 request ID、session/turn 身份、操作摘要和可接受的响应类型，投影成飞书交互，再校验点击者身份、请求有效期和是否已被处理，最后把结果回送给正确的原生请求。超时、取消、重启后的行为必须确定；不能把普通 choices 卡片点击当作审批成功。

**追问 2：多人同时点击批准，或转发卡片后有人点击怎么办？**

按请求做原子终态提交，限制有权限的人和适用会话，拒绝过期、重复及不匹配响应。结果必须绑定原操作，不能只接受一个通用“同意”字符串；原生 turn 已退出时也不能把迟到审批应用到下一轮。

**追问 3：先做 steering 有什么风险？**

当前跟进消息主要排队到下一轮。若接入执行中 steering，需要考虑消息归属、原生是否支持、返回确认、取消竞争和最终 transcript 顺序。不是把排队文字直接写进 stdin 就完成了能力等价。

**追问 4：如何在两周内交付可评估结果？**

选一个边界明确的场景，先固定验收，再做一条能力链路和最小可用反馈，最后进行故障与真实运行验证。明确不覆盖的后端与场景，不承诺两周完成通用企业 Agent 平台。

**依据**：E11、E16。

### L06：这个项目对前端工程师的价值在哪里？怎么判断你真的理解？

**主问题**

这主要是 Node 和进程管理，与你的前端背景有什么关系？

**首轮回答**

> 前端结合 Agent 的难点不只是聊天框，而是把长时间、部分失败、可取消的工作表示成可信的交互状态。流式事件、配置生效、操作权限、审批和交付反馈都需要跨前后端理解。我会重点展示自己对这些契约的分析或实际改动，而不是把别人的运行时实现改写成自己的履历。

**完整设计思路**

- 从用户任务建模：已收到、排队、运行、等待、取消中、交付、异常应可理解。
- 从协议建模：答案、活动、后台任务、终态不能混为一个 loading。
- 从管理面建模：配置保存、实际运行配置、进程是否重启是不同状态。
- 从类型和测试保障：对联合类型进行分支处理，模拟乱序和重复事件，测试恢复而非仅快乐路径。
- 从工程归属控制：BYO 目录不由管理面擅自改写，托管定义只更新明确所有权段落。
- 技术栈应忠于事实：当前管理 UI 是原生 JavaScript 静态 SPA，不是 React 应用。

**追问 1：如果让你重构 handler，会怎么做？**

先用现有行为和故障用例建立回归，找一个边界清楚的模块，例如卡片投递或入站准入，把隐式依赖改成显式接口；保持调用顺序、取消语义和降级不变。完成一个边界后再推进，不在没有验证的情况下同时拆多个状态源。

**追问 2：管理后台保存成功，是否就代表运行配置生效？**

不一定。需要区分配置源已持久化、托管文件投影完成、运行进程已加载和原生 session 是否重开。BYO 指令由项目 owner 维护，管理面不应该在别处保存一份文件后声称已经更新 BYO 行为。

**追问 3：要证明自己理解，面试现场可以做什么？**

沿一条真实路径定位文件和状态，解释异常时的表现，并在隔离 fixture 中增加一个回归用例或小改动。能够预测行为、定位失败和验证结果，比背诵模块名更有说服力。但只有真正执行过，才能称为个人实践。

**追问 4：技术 Leader 最想听到哪种取舍？**

能说明为什么先保持轻量部署、哪些复杂度交给原生 Agent、当前边界在哪里，以及出现什么信号后需要升级架构。不要把“未来可以加”说成“现在已经具备”。

**依据**：E11、E19、E20。

## 七、真实贡献与证据建设

### 7.1 什么才能支持“我参与了开发”

能够说明一个真实问题的来龙去脉：为什么要改、你修改了什么、与上游有什么区别、如何验证、出现哪些限制。

有效证据可以包括：

- issue、需求或清晰的复现材料。
- 自己实际完成的 diff、测试、设计记录与评审反馈。
- 在隔离环境运行的命令、版本、输入和结果。
- 上游 PR 及其讨论，或内部允许披露的真实二次开发材料。
- 修改前后的行为对照与失败证据。

不必一定等到 PR 合入才能说明“做过二次开发”，但必须准确区分“本地修改”“已提交 PR”“已合入”和“已部署”。下载源码、改作者名或提交一次没有实质内容的 commit，不能替代真实参与。

### 7.2 三个适合从前端背景切入的贡献方向

以下是候选方向，不是断言上游缺陷，也不是已经实施的任务。开始前应检查最新源码、相关 issue 和维护者意图，避免重复或不必要的改动。

#### 方向 A：排队与取消状态的可见性

**问题假设**：长任务后面的请求在等待时，用户可能不知道是否已经被接收。

**最小贡献范围**

- 在确认存在体验缺口的前提下，增加明确的排队反馈。
- 区分已接收、待执行、执行中和取消。
- 保持同会话串行、兼容消息合并与停止语义。
- 避免对每条事件过度发送卡片或反应，测量新增平台调用。

**验收**

1. A 执行时发送 B、C，能解释它们的等待与合并情况。
2. `/stop` 后被丢弃消息不会通过补取重新启动。
3. 其他话题不受影响。
4. 新反馈没有错误宣称精确队列位置或开始时间。

**能够展示的个人能力**：用户状态建模、TypeScript 异步流程、前后端契约、回归测试。

#### 方向 B：运行延迟与失败诊断视图

**问题假设**：已有分段指标不容易被维护者快速理解，可能把飞书等待误判为模型慢。

**最小贡献范围**

- 只读解析已有运行指标，展示排队、准备、runner 和投递阶段。
- 区分缺失数据、失败样本、首轮和续轮。
- 不把字符数展示成 token，不把 pooled 显示为“必然热启动”。
- 对敏感路径与日志字段进行脱敏或限制展示。

**验收**

1. 使用固定样本验证每个阶段计算。
2. 缺失、乱序、部分收尾、失败样本不被默认为 0 或成功。
3. 旧版指标兼容，页面不会因单行异常崩溃。
4. 对大文件采用有界读取或分页策略，不阻塞管理面。

**能够展示的个人能力**：可观测产品设计、数据语义、鲁棒 UI、性能与测试。

#### 方向 C：流式终态一致性的回归与小范围改进

**问题假设**：高频增量、最终快照、取消和投递失败之间存在值得补充的回归场景。

**最小贡献范围**

- 先检查已有测试，提出具体缺口，而不是随意重写卡片模块。
- 补充一个能说明实际风险的事件序列。
- 若复现了缺陷，提交最小修复与解释；若未复现，也保留真实结论。
- 对最终卡片和降级反馈做行为断言，不只断言调用次数。

**验收**

1. 终稿不被迟到增量覆盖。
2. 无变化内容不重复更新。
3. 取消后的过期事件不把界面改回运行中。
4. finalize 失败后用户能看到准确的结果与降级说明。

**能够展示的个人能力**：异步竞态分析、协议理解、测试设计、最小修复。

### 7.3 一份可审查的贡献记录模板

```text
基线版本：
问题来源与复现条件：
我的责任范围：
上游原有能力：
修改文件与关键设计：
为什么没有采用其他方案：
单元/模拟测试结果：
真实运行验证结果：
未执行或未通过的验证：
行为与资源开销变化：
PR/评审/部署状态：
仍然存在的限制：
```

“未验证”应保留，不应为了看起来完整而删除。

### 7.4 实施顺序

1. 选一个方向，核对最新版本与现有测试。
2. 在独立分支或工作区建立可复现 fixture，不改正式配置。
3. 先固定预期，再进行最小实现。
4. 执行纯测试与类型检查。
5. 需要真实 CLI、飞书或模型时，获得明确授权再验收。
6. 形成 diff、测试与设计说明，按实际情况提交上游或保留二次开发记录。
7. 只有到这一步，才据实讨论加入简历的贡献描述。

本文没有执行上述实施步骤，也没有制造提交、PR、部署记录或“参与证明”。

## 八、练习路线与自检

### 8.1 回答如何随追问逐层展开

第一层控制在约 30 秒，使用“问题、机制、边界”三句话。

第二层展开一条具体时序。例如收到消息后先 in-flight、何时进入 seen、失败如何释放，不要立即堆砌所有模块。

第三层讨论竞态和取舍。例如外部副作用已发生而完成记录未落盘，此时消息去重为什么不够。

第四层再谈验证和演进。说明如何复现、如何断言、需要什么额外能力。设计建议必须保持将来时。

面试官不继续追问时，在一个清楚的结论处停止；不要为了展示储备把所有答案连续背完。

### 8.2 技术面试官建议顺序

```text
T01 架构边界
  → T02 原生协议
  → T03 会话与并发
  → T04 消息恢复
  → T06 进程与取消
  → T07 流式 UI
  → T09 交接
  → T10 性能验证
```

对数据一致性感兴趣时，插入 T05；对业务流程感兴趣时，插入 T08。

### 8.3 Leader 建议顺序

```text
L04 业务场景和指标
  → L01 风险与权限
  → L03 验证与上线
  → L05 优先级
  → L02 容量演进
  → L06 个人能力与职责
```

### 8.4 四道白板题

1. 画出 local、WebSocket、gap-fill 三种副本进入同一消息准入入口的流程，标出崩溃窗口。
2. 画出取消意图、turn 结束、进程退出三个不同时间点，说明替代写者何时允许启动。
3. 写出 delta、snapshot、finalize 对答案缓冲和远端卡片的不同作用。
4. 设计“两个话题互相冲突”的真实测试，区分上下文串扰与文件冲突。

白板图应由自己解释，而不是只复述本文。可以准确指出当前方案没有解决的问题，也是一种能力。

### 8.5 面试前检查

- [ ] 能讲清楚一句话定位，且不冒领作者身份。
- [ ] 能从源码定位一次请求的入口、session、runner 和终稿路径。
- [ ] 能解释 queue key 与 session key 的区别。
- [ ] 能区分去重、恢复和业务幂等。
- [ ] 能区分 done、processExited、交付和验收。
- [ ] 能解释至少两条具体失败路径。
- [ ] 能说明原生审批、steering、文件隔离的现状。
- [ ] 能准确描述当前管理 UI 的技术栈。
- [ ] 没有跨项目挪用采用率、人效或成本数据。
- [ ] 个人开发贡献与测试结果都有真实证据；没有的就明确说没有。

## 最后结论

最有面试价值的不是“在飞书接了一个 AI”，而是理解并能解释：原生能力如何保留、并发如何不破坏会话、重复和失败如何恢复、长任务如何停止、结果如何准确交付，以及哪些事情仍必须由人和机械权限控制决定。

这份研读可以支持扎实的技术交流。要把它变成个人项目经历，还需要实际完成并验证一项清楚、可审查的贡献。
