# Agent 性能分析与优化记录

日期：2026-11-06。历史运行目录：`data/performance/20261106-01/`。
按用户要求，该目录的原始 profile、压测输出、隔离语料及测试会话已清理，
不再作为可访问证据提供；下文文件名仅说明历史测量方法与记录位置。
保留可复现工具、配置、必要静态样例和本报告中的汇总结果，未重新执行收费模型或压测。
正式语料、模型缓存及本地敏感配置未删除，也不提交 Git。

## 结论与范围

本轮执行真实 cProfile、Locust 及主控模型抽查，不使用假模型代替实测。
主要瓶颈是本地 CPU cross-encoder，而非已经得到证明的远程 API 并发不足。
采用精确推理 LRU、复用计数 Tokenizer、活跃片段快照缓存；
没有新增生产 FastAPI、多用户执行或改成并发访问同一 SQLite 连接。

压测覆盖两个知识助手的真实“读片段”和“Embedding → Milvus/BM25 → Reranker”路径。
HTTP 仅为 Locust 的 loopback 临时适配器，所有调用仍排入原有单一所有者线程。
没有压测远程模型、BOSS、简历 OCR/排版、完整面试或真实用户职业数据；
不能把本轮检索 QPS 称为整个求职 Agent 的端到端 QPS。

## 环境与方法

- Apple M1，8 逻辑核、16 GiB，macOS 26.0.1 arm64，Python 3.12.12。
- Locust 2.47.0，py-spy 0.4.3，ONNX CPUExecutionProvider，模型线程数保持 4。
- 基线代码：`6a9b98c4ee7d16acda3ea4781af79b17b3a5448b`。
  优化对应本报告所在提交；测量时为该基线后的工作区变更。
  当时各阶段的 `environment.json` 记录源码差异，原文件已随测试目录清理。
- 真实知识库副本 2059 片段、版本 16；题库副本 4500 片段、版本 643。
  SQLite 与 Milvus 使用隔离目录/命名空间，复用磁盘模型缓存。
- Embedding：`sentence-transformers/paraphrase-multilingual-mpnet-base-v2`。
  Reranker：`BAAI/bge-reranker-v2-m3-int8`。
  默认批大小不变：Embedding 16，知识重排 4，题库重排 8。
- 同一台机器顺序执行，1/4 并发，零思考时间，配置窗口 20 秒。
  QPS 分母为实际 test_start 到 test_stop，含在途请求排空，不固定除以 20。
  每个虚拟用户从同一位置循环五个固定技术主题；开始压测前先执行五主题预热。
- `retrieve` 不使用完整回答缓存；优化后允许精确推理缓存。
  `retrieve_uncached` 每请求清空查询向量和重排缓存，候选数、查询与模型不变；
  片段快照/词法索引缓存及磁盘模型缓存仍在，不称为全冷启动。

## Profiling 证据

独立 `*-direct-profile/retrieval.prof` 在调用线程执行，无 HTTP 服务：

| 基线，两次真实检索 | 总耗时 | ONNX run 累计 | 占观测耗时 |
| --- | ---: | ---: | ---: |
| 知识助手 | 21.777 s | 20.860 s | 95.8% |
| 题库助手 | 37.435 s | 36.471 s | 97.4% |

这是同步调用的耗时归因，不是硬件 CPU 利用率。知识侧重排路径累计 20.759 s，
重复克隆 Tokenizer 0.522 s，活跃片段读取 0.174 s；题库活跃片段读取 0.452 s。
`snapshot.prof` 另对 50 次片段读取计时。

最终代码的无推理缓存对照如下；两次检索结果 ID/顺序保持一致：

| 操作 | 知识：前 / 后 | 题库：前 / 后 |
| --- | ---: | ---: |
| 两次检索总耗时 | 21.777 / 22.274 s | 37.435 / 43.666 s |
| ONNX run 累计 | 20.861 / 22.052 s | 36.471 / 43.222 s |
| 50 次片段读取 | 1.243 / 0.344 s | 2.781 / 0.979 s |

片段读取确实减少工作；未命中检索没有表现出稳定加速，独立 profiling 的总耗时甚至更高。
新增开销不改变 ONNX 批组成或调用次数，但模型算子计时本身波动明显；
未控制热节流和后台负载，不能证明这一差值是代码回归或排除回归，需要多轮对照。
不以 Locust 的少量未命中样本挑选更好看的结果。

`measure` 内嵌的 `warm.prof` 在 Python 3.12 多线程环境混入了 HTTP 轮询等待，
因此仅留作辅助诊断，不用它计算推理占比。

py-spy 已实际尝试，但未成功采样：普通及沙箱外执行均返回
`This program requires root on OSX.`，`sudo -n` 返回 `sudo: a password is required`。
没有请求或获取用户密码，也没有修改 SIP；没有 py-spy 火焰图或采样结论。

## Locust 对照

所有数值以逐请求计时生成的汇总 JSON 为准，成功请求使用 nearest-rank，P99 单位为 ms，

### 相同场景，优化前与优化后

`N` 是成功请求数。热检索的巨大差异来自精确推理缓存，不是单次模型推理加速。
所有表格行请求失败数均为 0。

| 知识/片段读取 | 1 | 33.4366 | 255.8747 | 147.36 | 7.80 | 557 / 4993 |
| 知识/片段读取 | 4 | 45.7196 | 256.4493 | 211.53 | 58.21 | 900 / 5132 |
| 题库/片段读取 | 1 | 20.6353 | 121.0440 | 184.26 | 38.49 | 405 / 2400 |
| 题库/片段读取 | 4 | 21.5567 | 132.7930 | 367.15 | 74.29 | 427 / 2640 |
| 知识/重复主题检索 | 1 | 0.0616 | 18.5327 | 16345.61 | 230.98 | 2 / 365 |
| 知识/重复主题检索 | 4 | 0.0484 | 26.5715 | 82579.47 | 236.15 | 4 / 531 |
| 题库/重复主题检索 | 1 | 0.0586 | 18.3486 | 17346.28 | 94.28 | 2 / 365 |
| 题库/重复主题检索 | 4 | 0.0547 | 18.4686 | 73112.79 | 266.93 | 4 / 370 |

优化后四组重复检索分别完成 365/531/365/370 次，每次查询向量和重排均命中，
但仍执行真实混合检索与当前片段选择。基线没有这些推理缓存，因低吞吐只执行了
主题循环的少量前缀；不能将这组不同实际主题覆盖率的数据外推到真实流量。
真实 `ask` 路径原本也有完整答案缓存，本轮 `retrieve` 不使用它；
新增推理缓存相对真实线上答案缓存的额外收益取决于查询/历史分布，尚未测得。

## 实际改动

1. 两个助手查询向量及重排结果增加每实例 32 条的有界 LRU，容量 0 禁用。
   重排键包含模型、批大小、查询及完整有序文本，模型实例更换后清空。
   不按单条文档缓存分数，避免 INT8 批组成改变评分；不缓存失败/非法评分。
   返回列表副本，不允许调用者改写缓存；只在进程内，不落盘或进入共享语料。
2. 知识助手复用不截断的计数 Tokenizer，不修改模型的推理 Tokenizer。
   缓存命中仍按当前片段 ID 重算截断诊断，不复用过时引用。
3. 活跃片段缓存已解析 payload，每次返回独立 Chunk。
   `total_changes` 和 `PRAGMA data_version` 同时感知本连接及外部写入；
   事务内读取绕过缓存，防止回滚留下未提交内容。没有数据库迁移。
4. 暴露有边界校验的批大小与缓存容量配置。主配置未设置时保留各助手配置，
   不修改全局环境变量或真实 `.env`。完整答案缓存标识也包含重排批大小，
   首次切换本版时旧标识缓存不再命中，原条目按其 TTL 过期，不清空共享 Redis。

缓存只复用推理数学结果，来源检查、当前元数据、混合检索与最终引用仍逐请求执行。
未命中的新查询仍需完整 CPU 推理，未证明远程 LLM 或完整业务流程变快。
知识压测进程启动后另补了事务回滚防护和答案缓存批配置标识；
它们不改变该无事务、无完整回答缓存的检索压测路径，最终代码另经过普通回归及独立 profiling。

## 未采用的批处理调整

`tuning-knowledge.json` 对真实 16 候选、71–447 token 的输入进行单轮实验：

| Reranker 批大小/顺序 | 耗时 | 最大分数偏移 | 排序相同 |
| --- | ---: | ---: | --- |
| 4 / 原顺序 | 6.895 s | 0 | 是，参考 |
| 8 / 原顺序 | 8.058 s | 0.4647 | 否 |
| 16 / 原顺序 | 8.582 s | 0.4789 | 否 |
| 4 / 按长度分组 | 6.283 s | 0.7764 | 否 |

当前 INT8 模型对批组成敏感，因此不采用增大重排批或长度分组。
Embedding 16 文档测试：batch 8/16/32 分别 7.899/7.731/5.276 s，向量相同；
16 与 32 在这里实际上都是同一个 16 文档批，单次顺序计时存在噪声，
不能作为 batch 32 的吞吐收益证明，保持默认 16。

- `comparison.json` 核对两助手五主题和独立 profiling 的结果 ID/顺序、片段数、
  各轮正式库身份/版本，全部一致。版本检查不等于所有表逐字段未变；
  正式库只读，测试写入使用隔离副本及命名空间。
- 本轮未重跑完整终端 PTY、简历视觉、面试闭环或 BOSS 验收，不以普通测试代替它们。

真实主控抽查（技术问题、隔离会话、实际远程 GLM 与知识服务）：

| 阶段 | 耗时 | 样本 | 知识路由 | 引用 | sufficient / persisted |
| --- | ---: | ---: | --- | ---: | --- |
| 优化前 | 49.780 s | 1 | local | 3 | true / true |
| 优化后 | 46.856 s | 1 | local | 1 | true / true |

两次均实际调用主控与知识工具；调用前仅删除当前隔离语料、该精确问题的答案缓存键，
并从主应用保存记录核对路由不是 `cache`。`local` 指资料来自本地语料，不代表模型离线。
优化后产物显式记录路由；基线路由另从隔离 `runtime/leader.sqlite3` 保存记录只读核对。
生成内容及引用数存在随机差异，不声称逐字或答案质量等价；各一条不能计算有效 QPS/P99
或证明端到端加速。原始记录为 `baseline/`、`optimized/supervisor-smoke.json`。
最终再次只读核对正式库身份/版本未变，临时压测进程均已退出。

这是闭环短窗口表征，存在 coordinated omission，未控制热节流、其他系统活动，
没有多轮置信区间或开放式恒定到达率测试。少于 1000 个成功请求均标记 P99 样本不足；
基线完整检索仅 2/4 样本，P99 实际等同观测最大值，不是可靠尾延迟或 SLA。
预热五主题重复查询刻意呈现缓存收益，不代表新颖查询或真实流量命中率。
提高客户端并发并不会增加串行后端的模型算力。

下一步若要改善新颖查询，应在独立质量集上多轮比较 CPU 线程数、执行提供器或更轻的
多语言重排模型，再做开放式负载和较长窗口测试。更换模型/候选预算必须同时报告召回、
排序、引用覆盖与失败率，不能只以本轮热缓存 QPS 决定。

复现、隔离、单独 profiling、Locust 和离线一致性汇总命令见 [perf/README.md](perf/README.md)。
